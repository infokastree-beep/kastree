# These tests cannot run while both application URLs log in as production
# findraft (NOSUPERUSER, NOBYPASSRLS, not the table owner). The backend job
# still runs every one of them. Its login is a superuser, so RLS does not
# apply to its session and it can SET ROLE findraft_app.
#
# Not in the HTTP list, for the same reason:
# tests/test_findraft_tenant_isolation.py
#   Every test asserts the login is superuser and then SET ROLE findraft_app.
#   Cleanup also DISABLE TRIGGER, which only the table owner can do.
# tests/test_companies_migration.py::test_rls_disable_rolls_back_when_transaction_aborts
#   ALTER TABLE ... DISABLE ROW LEVEL SECURITY. The production login is not
#   the table owner. The rest of that file drives Alembic, not the HTTP API.
#
# Two shapes below. (1) SET ROLE findraft_app or DISABLE TRIGGER. Production
# provision does not create findraft_app, and only the table owner can
# disable a trigger. (2) The test's own SQL does not call set_rls_org_id.
# Product 1 policies then cast current_setting('app.current_org_id') and
# raise invalid input syntax for type uuid: "". Newer policies use NULLIF
# and return no rows, so a follow-up count or scalar_one fails. The HTTP
# status in those tests had already succeeded. The assertions were not
# changed.
